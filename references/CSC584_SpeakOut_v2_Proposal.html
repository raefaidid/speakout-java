1.0 Project Overview

SpeakOut v2 is a semester project for CSC584 Enterprise Programming that continues the domain of the team’s earlier SpeakOut initiative: a school-safe channel for students and teachers to record and manage bullying-related incidents responsibly. Version 1 (CSC577) was broad in scope (web and mobile clients, Python services, and advanced analytics such as text classification and clustering). Version 2 deliberately narrows scope to satisfy the course rubric: a single standards-based Java web application using JavaBeans (Model), JSP (View), and Servlets (Controller) with session-based login/logout, registration with validation, full CRUD on persisted data, and a role-aware dashboard with charts and summaries.

The system is multi-school: each user belongs to a school; aggregated dashboards for institutional administrators can compare volumes and resolution outcomes without duplicating a separate deployment per school. Students can submit incident reports; designated school staff (teachers / case handlers) triage reports, add structured notes, and transition statuses; administrators monitor KPIs (e.g., cases per category, trends over time, resolution rates).

The presentation layer follows Bootstrap 5 for a responsive, consistent navigation experience, with Chart.js on administrator dashboards. Server pages use JSTL and Expression Language so that business logic remains in Servlets and JavaBeans rather than JSP scriptlets. Source code is managed in GitHub using branches and pull requests aligned to the four-member team structure.

Team (four members): one Product Owner (backlog and acceptance criteria), one Lead Developer (architecture, integration on GlassFish, reviews), and two Developers (feature delivery). Technology (course brief): JDK 21 GlassFish 8 JavaBeans JSP + JSTL/EL Servlets JDBC Bootstrap 5 Chart.js GitHub — no Spring.

2.0 Problem Statement

  • Under-reporting & fear of retaliation: Students who experience or witness bullying may avoid reporting if the process is unclear, intimidating, or perceived as non-confidential among peers.
  • Inconsistent handling across classes and schools: Without a shared case record, follow-up actions, status, and accountability vary; multi-school environments amplify coordination challenges.
  • Limited visibility for leadership: School administrators need timely, trustworthy summaries (category mix, response times, outcomes) to allocate counselling resources and prevention programmes.
  • Course-aligned delivery gap: Prior work used a heterogeneous stack; the enterprise programming course requires a focused Jakarta EE-style MVC implementation on JDK 21 and GlassFish 8 without Spring, which v2 addresses explicitly.

3.0 Objective

  • Deliver a secure web application with Login/Logout using HttpSession and role-aware authorisation (student, teacher/case handler, administrator).
  • Implement registration with validation (client-side feedback and server-side rules for email format, password strength, uniqueness, and required fields).
  • Provide information management (CRUD) for incident reports and teacher case notes, including search/filter, status transitions, and confirmations for destructive actions.
  • Build dashboards with multiple representations (KPI cards, charts, recent activity lists) so each role gains operational insight.
  • Model multi-tenancy by school in the database and enforce it in DAO/Servlet layers.
  • Prepare storyboard HTML (already available under mockups/) and a clear path to final JSP screens using the same visual system.

Future work (outside README requirements): capabilities from SpeakOut v1 such as mobile apps, separate Python/ML services (TF‑IDF, sentiment, clustering), generative assistance, and evidence file uploads are deferred so v2 remains feasible under the four core modules; they may be proposed as a later phase after the enterprise web platform stabilises.

4.0 Proposed User Interface

The following five (5)+ interfaces satisfy the template requirement and map directly to course modules. Full interactive wireframes are implemented as static HTML in the repository (speakout_v2/mockups/), sharing a Bootstrap-based design system (indigo primary, teal accent).

1. Login

Session creation, role entry, validation errors. Logout invalidates session.

2. Registration

Student/teacher signup with school selection; inline valid/invalid states mirror server-side ValidationUtil.

3. Student dashboard

KPIs, recent reports, quick actions, help resources; entry to create/list/detail flows.

4. Incident report form (Create/Update)

Category, narrative, privacy/anonymity preferences; reused JSP for edit via presence of report ID in scope.

5. Administrator dashboard

Cross-school KPI cards, Chart.js visualisations, school table — satisfies “different data representations”.

6. Teacher case workspace (bonus clarity)

Assigned cases, filters, detail page with notes CRUD and status changes — maps to staff-side CRUD & read pathways.

Additional screens in mockups/ (report list, read-only student detail with timeline, user profile/password) strengthen the storyboard and demonstration of navigation consistency.

5.0 Database Design

Persistence uses a relational database (e.g., MySQL 8 or MariaDB) via JDBC. Early development will use a DriverManager-backed utility class for simplicity; the connection acquisition can later be refactored to a GlassFish JDBC resource and JNDI lookup without rewriting DAO contracts.

Relationship summary:

  • School 1 — * User: every account is anchored to one school for multi-school reporting.
  • User 1 — * Incident_report (as student): students author many reports.
  • School 1 — * Incident_report: enforces tenant boundary for queries and dashboards.
  • Category 1 — * Incident_report: normalised category dimension for analytics.
  • Incident_report 1 — * Case_note: teachers append structured notes; supports CRUD on notes and status changes on the parent report.
